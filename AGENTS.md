# exprit: guide for AI agents

exprit (`@syncrea/exprit`) is a TypeScript-first expression parser and
evaluator. It is a drop-in replacement for [expr-eval](https://github.com/silentmatt/expr-eval)
and adds a second, JavaScript-flavoured syntax dialect. This file is the entry
point for any agent working in the repo. Read it fully before changing code.

## Non-negotiable rules

1. **Follow [docs/typescript.md](docs/typescript.md).** It covers functional
   style, `readonly` interfaces, no enums, named exports only, `unknown` over
   `any`, and JSDoc on public APIs. Lint enforces most of it. Do not edit that
   file unless the user asks.
2. **Never execute code.** No `eval`, no `new Function`, no `with`, and no
   generated JavaScript source. The evaluator interprets a whitelisted AST,
   and that is the whole security model.
3. **Never widen the sandbox by accident.** Member access goes through
   `readMember` (`packages/core/src/lib/member-access.ts`). Identifiers go
   through the registry's resolver. Blocked names (`__proto__`, `prototype`,
   `constructor`, ...) stay blocked everywhere. Only non-mutating methods
   belong in `DEFAULT_SAFE_METHODS`. Any change here needs a test in
   `packages/exprit/src/lib/security.spec.ts`.
4. **Drop-in is the contract.** The legacy dialect must keep passing
   expr-eval's own test suite (`pnpm conformance`). `toString()` output in the
   legacy dialect must match expr-eval byte for byte. A deliberate difference
   goes into `packages/exprit/conformance/known-deltas.ts` **and**
   [docs/differences-from-expr-eval.md](docs/differences-from-expr-eval.md).
5. **Respect the dependency direction** (enforced by `@nx/enforce-module-boundaries`):
   `core` ← `tokenizer` ← `parser-*`; `core` ← `registry`; everything ←
   `exprit` ← `cli`. `core` depends on nothing.
6. **Do not touch vendored files.** `packages/exprit/conformance/expr-eval/**`
   is generated by `tools/scripts/vendor-expr-eval-tests.mjs`.

## Public API layers

1. **Functional API (preferred):** `createEnvironment`/`extend` build frozen
   environments, `parse` returns frozen `ParsedExpression` values, and pure
   functions (`evaluate`, `compile`, `simplify`, ...) work on them. Variables
   are never mutated.
2. **`CompatParser` / `CompatExpression`:** expr-eval's class API, a thin
   layer over (1). `Parser` and `Expression` are deprecated aliases kept for
   drop-in. Do not add features here that the functional API lacks.
3. **`@syncrea/exprit/core`:** low-level building blocks (parsers, registries,
   AST evaluation). Public for advanced users.

## Map of the repo

| Path                     | Package                        | What lives there                                                                                       |
| ------------------------ | ------------------------------ | ------------------------------------------------------------------------------------------------------ |
| `packages/core`          | `@exprit/core` (internal)      | AST types, token types, evaluator, closure compiler, transforms, member access, errors                 |
| `packages/tokenizer`     | `@exprit/tokenizer` (internal) | One configurable scanner plus `LEGACY_` / `MODERN_TOKENIZER_CONFIG`                                    |
| `packages/parser-legacy` | `@exprit/parser-legacy` (int.) | Pratt parser for expr-eval syntax, `printLegacy` (expr-eval `toString` format)                         |
| `packages/parser-modern` | `@exprit/parser-modern` (int.) | Pratt parser for the JavaScript expression subset, `printModern`                                       |
| `packages/registry`      | `@exprit/registry` (internal)  | Operators, functions, constants, safe globals, per-dialect identifier resolution                       |
| `packages/exprit`        | `@syncrea/exprit` (published)  | Functional API (`api.ts`, `environment.ts`), `CompatParser` compat class, `/core` subpath, conformance |
| `packages/cli`           | `@syncrea/exprit-cli` (publ.)  | `exprit` command: one-shot, stdin, REPL                                                                |
| `docs/`                  |                                | Architecture, dialects, differences from expr-eval, TypeScript guidelines                              |
| `tools/scripts/`         |                                | Repo scripts (vendoring the conformance suite)                                                         |

Read [docs/architecture.md](docs/architecture.md) before changing the
pipeline, and [docs/dialects.md](docs/dialects.md) before changing either
grammar.

## Commands

Always run tasks through Nx with pnpm (`pnpm nx ...`), never the tools directly.

| Goal                                   | Command                                                       |
| -------------------------------------- | ------------------------------------------------------------- |
| Everything CI runs                     | `pnpm check`                                                  |
| One project                            | `pnpm nx test parser-modern` (or `lint`, `typecheck`)         |
| expr-eval conformance (sources)        | `pnpm conformance`                                            |
| Conformance against the built bundle   | `CONFORMANCE_TARGET=dist pnpm nx run exprit:conformance`      |
| Conformance baseline against expr-eval | `CONFORMANCE_TARGET=expr-eval pnpm nx run exprit:conformance` |
| Build published packages               | `pnpm build`                                                  |
| Try the CLI                            | `node packages/cli/dist/main.mjs -d modern "1 + 1"`           |
| Format                                 | `pnpm format`                                                 |
| Release (asks first)                   | `pnpm nx release --dry-run`                                   |

## Definition of done

- [ ] `pnpm check` passes: lint, typecheck, test, build, conformance.
- [ ] New behaviour has tests in the library that owns it. Security-relevant
      behaviour also has tests in `security.spec.ts`.
- [ ] If a new AST node was added, every exhaustive `switch` handles it. The
      compiler tells you where: evaluate, compile, transform (mapChildren and
      linearize), and both printers.
- [ ] `evaluate` and `compile` agree. `core/src/lib/evaluate.spec.ts` runs both.
- [ ] User-visible changes are reflected in `docs/` and in the package README.

## Common tasks

Step-by-step playbooks live as skills in `.claude/skills/`:

- `extend-grammar`: add syntax or an AST node to a dialect
- `add-builtin`: add an operator, function, constant or safe method
- `conformance`: run, triage and update the expr-eval conformance suite
- `release`: version and publish with `nx release`

Agents without skill support can read the `SKILL.md` files directly.

# General Guidelines for working with Nx

- For navigating/exploring the workspace, invoke the `nx-workspace` skill first - it has patterns for querying projects, targets, and dependencies
- When running tasks (for example build, lint, test, e2e, etc.), always prefer running the task through `nx` (i.e. `nx run`, `nx run-many`, `nx affected`) instead of using the underlying tooling directly
- Prefix nx commands with the workspace's package manager (e.g., `pnpm nx build`, `npm exec nx test`) - avoids using globally installed CLI
- You have access to the Nx MCP server and its tools, use them to help the user
- For Nx plugin best practices, check `node_modules/@nx/<plugin>/PLUGIN.md`. Not all plugins have this file - proceed without it if unavailable.
- NEVER guess CLI flags - always check nx_docs or `--help` first when unsure

## Scaffolding & Generators

- For scaffolding tasks (creating apps, libs, project structure, setup), ALWAYS invoke the `nx-generate` skill FIRST before exploring or calling MCP tools

## When to use nx_docs

- USE for: advanced config options, unfamiliar flags, migration guides, plugin configuration, edge cases
- DON'T USE for: basic generator syntax (`nx g @nx/react:app`), standard commands, things you already know
- The `nx-generate` skill handles generator discovery internally - don't call nx_docs just to look up generator syntax
